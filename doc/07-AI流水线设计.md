# 07 AI 流水线设计（研究板块 · 因子→模型→回测→评估 自动闭环）

> 目的：在「研究」板块新增 **AI 流水线（AI Pipeline）** 功能，把「因子生成 → 因子选择 → 模型训练 → 数据回测 → 效果评估 → 好模型入库 / 差模型诊断（训练参数问题 vs 因子选择问题）→ 迭代直至耗完执行轮次」这一整条链路由 AI 自动驱动，形成"目标 → 多轮自进化 → 产出合格模型"的研究闭环。
> 本文是 `doc/06` 中 **R6③「实现目标策略指标（目标指标 → 多轮迭代 → 收敛/预算）」** 与 **R5「ML 多因子回测」** 的落地设计。
> 基线代码：`backend/src/app/{agent,factor,strategy}/...`、`frontend/src/{views,api}/...`。

## 1. 需求解读与澄清

用户原始描述里隐含 4 个易混淆的"轮次 / 数据"概念，先规范为统一字段名：

| 用户原话 | 规范含义 | 字段名 |
|---|---|---|
| 轮次 | 单轮内 LLM 生成的因子个数 | `factor_count_per_round`（默认 4） |
| 测试数据 | 因子研究 + 模型训练用的数据区间（含时序 train/test 切分） | `research_window` |
| 回测数据 | 独立、样本外的回测区间 | `backtest_window` |
| 流水线执行轮次 | 整条大循环迭代几轮 | `max_rounds`（默认 5） |

已确认的 3 项关键决策：

1. **执行模型**：异步后台任务（ARQ worker）+ SSE 进度实时推送，可手动停止。单轮含多次 LLM 调用 + 训练 + 回测，秒级接口即时返回 `run_id`，前端订阅进度。
2. **数据边界**：**强制回测区间晚于训练区间**（严格样本外，防未来函数）。启动时校验 `backtest_window.start >= research_window.end`（或对训练期外的独立回测标的做显式豁免提示），不满足则拒绝启动。
3. **交付顺序**：先落本设计文档，评审后实现。

## 2. 现状盘点（可复用能力映射）

流水线 8 个阶段里，除「编排 + 轮次循环 + 失败诊断分支」外，其余单步能力**均已存在**，直接复用：

| 阶段 | 现有函数 | 位置 | 复用方式 |
|---|---|---|---|
| 因子生成 | `generate_factor_draft` / `generate_factor_idea` | `agent/service.py:676/756` | 直接调（含沙箱校验 + 自动重试） |
| 因子实测 | `run_factor_research_batch` | `factor/service.py:441` | 直接调（IC/RankIC/衰减，落库） |
| AI 因子选择 | `pick_factors` | `agent/service.py:229` | 直接调（LLM 精筛 + 规则兜底） |
| 模型训练 | `train_factor_model` / `run_ml_research` | `factor/service.py:476`、`ml.py:304` | 直接调（ridge/gbdt，OOS 指标 + artifact） |
| 训练诊断 | `review_training` | `agent/service.py:487` | 直接调（返回 `grade/keep/drop/params/agg_keep`） |
| 模型入库 | `persist_trained_model` | `factor/service.py:530` | 直接调 |
| 回测 | `run_backtest_vectorized` + `ml_score` 模板 + `_materialize_ml_scorer` | `strategy/engine/runner.py`、`templates.py:131`、`job.py:27` | 新增"不落策略库直接回测"入口（见 §5） |
| 回测复盘 | `review_backtest_task` / `review_backtest` | `agent/service.py:821/619` | 直接调 |
| 进度推送 | Redis pub-sub `ws:backtest:{id}` + 网关 SSE | `strategy/engine/job.py:73` | 复制该模式为 `ws:pipeline:{id}` |

**关键发现**：`ml_score` 隐藏模板已能对"未入库模型 artifact"回测（`_materialize_ml_scorer` 注入 `features / _booster / _flip`），但现有入口 `start_backtest` 要求先有 strategy+version。流水线需新增一条 **`run_pipeline_backtest`**：直接用刚训练的 artifact 回测（内存完成，不落 backtests 表，见 §5.3）。

**两个需补的能力缺口**（否则逻辑错误）：

1. `train_factor_model`（公开服务）**不返回 artifact**，而回测与入库都需要 artifact → 新增 `train_factor_model_full`（`run_ml_research(return_artifact=True)`）。
2. `persist_trained_model` 内部会**重新训练**（`run_ml_research(return_artifact=True)`）——流水线若先训一次、入库再训一次，既浪费又可能导致入库模型 ≠ 回测模型。→ 抽出 `persist_model_artifact(db, *, name, ..., artifact, resp, ...)`（只写 DB + pickle，不重训），`persist_trained_model` 与新流水线共用。

## 3. 需求规格

### 3.1 页面配置项（PipelineConfig）

| 配置项 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `name` | str | 自动 | 流水线名称（默认 `流水线-{时间戳}`） |
| `objective` | str(选填) | 空 | 研究目标（自然语言），空则每轮 `generate_factor_idea` 随机灵感 |
| `llm_model_id` | str(选填) | 默认供应商 | 指定 LLM |
| `research_symbols` | list[str] | `["BTCUSDT"]` | 研究/训练标的（多标的） |
| `research_interval` | str | `1d` | 研究/训练粒度 |
| `research_start/end` | datetime | 近 400 天 | **测试数据**窗口 |
| `backtest_symbol` | str | 取 research 主标的 | **回测标的**（单标的） |
| `backtest_interval` | str | 同 research | 回测粒度 |
| `backtest_start/end` | datetime | research 结束之后 | **回测数据**窗口 |
| `factor_count_per_round` | int(1~5) | 4 | 每轮生成因子数 |
| `max_pick` | int(2~12) | 6 | 进入模型因子数上限 |
| `max_rounds` | int(1~20) | 5 | **流水线执行轮次** |
| 初始超参 | dict | 同 `MlTrainReq` 默认 | model/horizon/test_ratio/alpha/max_corr/…，允许 AI 调参 |
| 效果阈值 | dict(可展开) | 见 §3.4 | 判定"合格"的可配置阈值 |
| `stop_on_excellent` | bool | true | 达到"优秀"阈值提前终止 |

### 3.2 状态机

**run 级**：

```
pending → running → succeeded（找到合格模型）
                  ├→ finished（轮次耗尽无合格）
                  ├→ failed（硬失败，保留已完成轮次）
                  └→ stopped（用户手动停止）
```

**round 级**：每轮 `phase ∈ {gen, research, select, train, backtest, evaluate, persist, diagnose}`，`status ∈ {pending, running, done, failed, skipped}`。

进度经 Redis `ws:pipeline:{run_id}` 逐阶段推送（见 §5.4），前端按"轮次卡片 × 阶段步骤条"实时渲染。

### 3.3 单轮执行流程

1. **gen（因子生成）**：LLM 依据 `objective` + 上一轮诊断负反馈（drop 的因子思路）生成 `factor_count_per_round` 个草稿 → 沙箱校验 → 去重（与本轮 / 历史 / 因子库现有）→ **`join_user_factor` 以 draft 状态入库**（获得稳定 UUID 作为 code，便于去重、`pick_factors` 给 LLM 更清晰的 name/tags 上下文、训练/回测按 id 引用；多行表达式不经"原始表达式当 code"的脆弱路径）。
2. **research（因子研究）**：对候选池（本轮新 + 历史 `keep` 保留）跑 `run_factor_research_batch`，得 IC/RankIC/衰减。
3. **select（因子选择）**：`pick_factors` 精筛出 ≤ `max_pick` 个进训练池（LLM 失败自动规则兜底；候选 < 2 个时本轮按"因子选择问题"处理并多生成因子）。
4. **train（模型训练）**：`train_factor_model`（research_window）→ OOS IC/RankIC/价差/命中率 + artifact（`return_artifact=True` 路径）。
5. **backtest（数据回测）**：用 `backtest_window` 对刚训模型跑 `ml_score`（严格样本外）→ 夏普/回撤/收益/交易数。
6. **evaluate（效果评估）**：综合训练 OOS 指标 + 回测指标给 `grade`。
   - `ok` → **persist（入模型库）**；满足"优秀"阈值则更新全局 best 并可提前终止。
   - `warn/bad` → **diagnose（失败诊断）**。
7. **diagnose（失败诊断）**：`review_training` + `review_backtest` 联合判定根因（见 §3.5），产出下一轮调整策略。
8. 推进 `round+1`，评估终止条件（§3.6）。

### 3.4 效果评估标准（双层判定）

> 口径修正：回测指标里没有 `net_return`（回测 `total_return` 已含手续费/滑点，天然是净收益）；`max_drawdown` 在 `metrics.py` 中是**负值**（`dd.min()`），故阈值用 `>= -0.20` 表达。

**模型层**（复用 `review_training` 的 ok 基准）：

- `oos_rank_ic ≥ 0.02` 且 `spread > 0` 且 `hit_rate ≥ 0.5` 且 `overfit_gap < 0.06`。

**回测层**（可配置阈值，默认；`sharpe` 为年化值）：

- `total_return > 0` 且 `sharpe ≥ 0.5` 且 `max_drawdown >= -0.20` 且 `num_trades ≥ 3`（排除"全程空仓/一锤子"）。

**分级**：

- 模型层 + 回测层都过 = `ok`（合格）；
- 只过一层 = `warn`；
- 都不过 = `bad`。
- "优秀"阈值（用于 `stop_on_excellent` 提前终止）：默认 `ok` 且 `sharpe ≥ 1.0` 且 `max_drawdown >= -0.12`。

### 3.5 失败诊断分支（训练参数 vs 因子选择）

判定依据（现有指标已足够，不引入新计算）：

- **倾向「训练参数问题」**：`overfit_gap` 大、LightGBM 学习曲线 OOS loss 拐点早、`degenerate=true`、train/test 量级失衡、价差为正但强度不足。
- **倾向「因子选择问题」**：单因子 OOS IC 普遍弱 / 方向与组合相反、`feature_filter.removed` 因子多、研究阶段因子本身 IC 就弱。

产出与下一轮动作：

- 参数问题 → 采用 `review_training` 返回的 `params`，下一轮**同因子子集、调参重训**。
- 因子问题 → 采用 `review_training` 的 `keep/drop`，下一轮**换/精筛因子**，并把 drop 因子的 `name/description/思路` 作为**负反馈注入 gen 阶段 prompt**（"上一轮这些思路已被证伪，请换方向"）。
- 两者兼具 → 优先处理因子（换因子），再叠加参数微调。

诊断结果 `{root_cause, keep, drop, params, review, advice}` 持久化到 round 记录，供前端展示与后续轮次引用。

### 3.6 终止条件（优先级从高到低）

1. 用户手动停止（`stop`）。
2. 出现合格模型且达"优秀"阈值（`stop_on_excellent`）→ `succeeded`。
3. 连续 `k` 轮（默认 3）无提升且诊断结论重复 → 收敛，`finished`。
4. 达到 `max_rounds` → `finished`。
5. 硬失败（数据不足 / 无可用 LLM / 回测窗口校验失败）→ `failed`，保留已完成轮次记录。

### 3.7 模型入库策略

- 仅 `grade=ok` 的模型 `persist_trained_model` 入库；模型名带 `流水线名 · round{round_no}` 前缀。
- 每轮 `keep` 因子**可选** join 到因子库（draft 状态），默认关闭，避免污染因子库。
- 全局维护 `best_model_id` / `best_metrics`，流水线结束后前端可跳转模型库查看。

## 4. 数据模型

新增迁移 `0012_pipeline.py`（Alembic）。两表均为 JSON 承载明细，避免每阶段独立建表：

```sql
CREATE TABLE pipeline_runs (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name          VARCHAR(120) NOT NULL,
    config        JSONB NOT NULL,           -- PipelineConfig（§3.1）
    status        VARCHAR(20) NOT NULL DEFAULT 'pending',  -- pending/running/succeeded/finished/failed/stopped
    current_round INTEGER NOT NULL DEFAULT 0,
    best_model_id UUID NULL,                -- 指向 ml_models.id
    best_metrics  JSONB NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at    TIMESTAMPTZ NULL,
    finished_at   TIMESTAMPTZ NULL
);

CREATE TABLE pipeline_rounds (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    pipeline_run_id  UUID NOT NULL REFERENCES pipeline_runs(id) ON DELETE CASCADE,
    round_no         INTEGER NOT NULL,
    phase            VARCHAR(20) NOT NULL DEFAULT 'gen',
    status           VARCHAR(20) NOT NULL DEFAULT 'pending',
    factors_generated JSONB NULL,           -- [{code,name,description,expression}]
    factors_picked    JSONB NULL,           -- [{code,reason}]
    train_result      JSONB NULL,           -- run_ml_research 精简结果（oos_ic/rank_ic/spread/hit_rate/...）
    backtest_summary  JSONB NULL,           -- 回测 metrics + 抽稀 equity 曲线（内存回测，不落 backtests 表）
    diagnosis         JSONB NULL,           -- {grade, root_cause, keep, drop, params, review, advice}
    model_id          UUID NULL,            -- 入库后指向 ml_models.id
    error             TEXT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (pipeline_run_id, round_no)
);
```

> `pipeline_runs` 另加 `factor_pool JSONB DEFAULT '[]'`：跨轮保留的候选因子 code 列表（诊断 `keep` + 每轮新生成），因"一轮一 job"无法依赖内存，需持久化在 run 行上。

`orm.py` 的 `_reflect_all` 名单追加 `"pipeline_runs", "pipeline_rounds"`，并新增对应 `*_table()` 访问函数。

## 5. 后端设计

新目录 `app/pipeline/`，分层遵循现有约定（API 只做参数/错误映射，业务在 service，SQL 在 repo）。

### 5.1 `pipeline/repo.py`

`PipelineRunRepository` / `PipelineRoundRepository`：create / get / list / update_status / update_round / set_best / list_recent，风格对齐 `factor/repo.py` 与 `strategy/engine/repo.py`。

### 5.2 `pipeline/service.py`（编排核心）

```
start_pipeline(db, config) -> run_id
    校验：end>start；backtest_window.start >= research_window.end（强制样本外）；
          至少 1 个 research 标的；max_rounds 合法。
    建 run(status=pending) + 第 0 轮占位 → 入队 run_pipeline_round_task(run_id, 1) → 返回 run_id。

run_round(db, run, round_no, ctx) -> round_result
    gen → research → select → train → backtest → evaluate → (persist | diagnose)
    每阶段 update_round + publish 进度；任何单步异常按"硬失败"处理并记录 error。
    训练用 factor.service.train_factor_model_full（返回 artifact）；入库用 factor.service.persist_model_artifact（不重训）。

evaluate(train_result, backtest_metrics, thresholds) -> (grade, checks)
diagnose(train_result, backtest_metrics, features, config, backtest_review) -> diagnosis   # 调用 review_training + review_backtest
should_terminate(run, round_result, ...) -> bool
```

> 诊断提示增强：`review_training` 会读取 `oos_charts.monotonic_r / q5_end / q1_end`，但 `run_ml_research` 的 `_build_oos_diag` 未产出这三项（只给 scatter/deciles/nav）。流水线服务在构建 review payload 前，从 `deciles` 算单调相关 `r`、从 `nav` 取 q5/q1 终点，补齐后再喂给 LLM，让诊断更准。

**负反馈注入**：`diagnose` 产出 `drop` 因子后，把其 `name/description` 拼进下一轮 `gen` 的 prompt，实现"证伪思路不再重试"。

### 5.3 `pipeline/worker.py`（ARQ 任务）+ 回测路径

> **关键修订**：ARQ worker `job_timeout = 1800`（30 分钟），整条流水线不能作为一个 job（会超时被杀）。改为 **一轮 = 一个 ARQ job**：`run_pipeline_round_task(run_id, round_no)` 跑完一轮后，若未终止则自行 `enqueue_job` 下一轮，否则标记终态。停止 = 置 `status='stopped'`，下一轮任务开跑前检查状态即退出。

```
async def run_pipeline_round_task(ctx, run_id: str, round_no: int):
    # 开跑前检查 run.status ∈ {stopped, failed} → 直接退出
    # 执行 run_round(...)；每阶段 publish 进度到 ws:pipeline:{run_id}
    # 判终止（§3.6）：终止 → 置终态；否则 enqueue_job(run_pipeline_round_task, run_id, round_no+1)
```

**回测路径 `run_pipeline_backtest`**（放 `pipeline/backtest.py`，不落策略库、不落 backtests 表）：

> **关键修订**：`backtests.strategy_id/version_id` 为 `NOT NULL`，流水线没有策略/版本，无法直接写 `backtests` 表；也不应污染策略库。故流水线回测**在内存完成**，结果（metrics + 抽稀 equity 曲线）存 `pipeline_rounds.backtest_summary` JSON；LLM 复盘用构造好的 dict 直接调 `review_backtest`（不依赖 DB 回测行）。

- 入参：`symbol/interval/start/end` + 刚训练的 `artifact`（含 `features / flip / booster`）。
- 加载 K 线 → 注入 `agg:*` 列（复用 `ml._load_fine_agg`，同 `run_backtest_job`）→ `run_backtest_vectorized(template_id="ml_score", params={"features","_flip","_booster","window","enter_q","exit_q"})`。
- 返回 `{metrics, equity_points(抽稀), summary}`，写入 round 记录；`review_backtest(db, {summary:{symbol,interval,metrics,final_equity}, symbols:[symbol], start_time, end_time, status})` 复用复盘。

注册：`arq_app.WorkerSettings.functions` 追加 `run_pipeline_round_task`。

### 5.4 进度协议（复刻回测 SSE）

- Redis 频道 `ws:pipeline:{run_id}`，消息：


- 网关 SSE 端点（对齐现有回测 SSE 通道）按 `run_id` 订阅转发。

## 7. 关键决策与风险护栏

| # | 决策/风险 | 说明与对策 |
|---|---|---|
| R1 | **LLM 成本** | 每轮 ≥4 次 LLM 调用（生成 + 选因子 + 训练诊断 + 回测复盘），跑满轮次 token 可观。对策：① 单步 LLM 失败自动降级规则兜底（沿用 `pick_factors`/`review_training` 的 fallback）；② 选因子/诊断支持跳过纯规则；③ 用量自动记入 `llm_usage`（沿用 `record_usage`），前端用量页可回溯。 |
| R2 | **死循环 / 烧钱** | 加 `max_rounds` 硬上限 + 单轮超时 + `stop` 手动停止 + 收敛判定（连续 k 轮无提升终止）。 |
| R3 | **未来函数** | 强制 `backtest_window.start >= research_window.end`；若回测标的不在训练标的集中，允许提前但需显式提示。 |
| R4 | **回测与训练口径一致** | 回测必须复用训练时的特征标准化（mean/std/clip）+ `flip` 方向 + gbdt booster，由 `ml_score` 模板 + artifact 注入保证。 |
| R5 | **模型库污染** | 仅 `ok` 入库；非 ok 的 artifact 不落盘（内存用完即弃）。 |
| R6 | **单轮超时 / 资源** | 一轮一个 ARQ job（避免 30 分钟 job_timeout 被杀）；LightGBM/大窗口训练 CPU 密集，`max_jobs=3` 天然限流。 |
| R7 | **因子库污染** | 每轮生成的因子以 draft 入库（稳定 id），仅最终入库模型的 `keep` 特征因子长期留存；draft 因子可被用户手动清理。 |
